## [BLOCKER]

1. 위치: `src/cli.ts:46-55`, `src/vault.ts:192-200`

문제: `<root>/wiki` 자체가 심볼릭 링크이면 외부 디렉터리를 정상 볼트로 인식한다.

근거:

```text
root/wiki -> /tmp/outside
/tmp/outside/secret.md
```

`resolveRoot()`는 `stat()`로 디렉터리 여부만 확인하고, `walkMd()`는 `baseReal = realpath(base)` 후 파일이 `baseReal` 하위인지 검사한다. 따라서 `/tmp/outside/secret.md`가 내부 파일로 승인되어 검색·pack으로 유출된다. 현재 P2-21은 `wiki/leak.md`, `wiki/leakdir`만 시험하고 `wiki` 자체 링크를 시험하지 않는다.

제안: `rootReal`과 `wikiReal`을 모두 구하고 `path.relative(rootReal, wikiReal)`가 정확히 `wiki` 디렉터리 내부인지 검증하라. `wiki` 자체 symlink는 거부하거나 명시적으로 허용 정책을 정하라. 테스트에 `root/wiki -> outside`를 추가하라.

문제: 개별 항목 상한은 있으나 요청 전체 크기와 총 메모리 사용량 상한이 없다.

근거:

- `terms` 문자열은 분할 전 길이 제한이 없다.
- `slugs` 문자열도 동일하다.
- 배열은 수백만 항목을 순회한 뒤에야 `>10`, `>30`을 감지한다.

- Markdown이 아닌 파일·디렉터리 수와 디렉터리 깊이에는 상한이 없다.

공격 예:

```json
{"terms":"a a a ... (수백 MB)"}
{"slugs":["x","x", "... 수백만 항목"]}
```

제안: raw 문자열/배열 직렬화 크기, 배열 길이, 디렉터리 수·깊이, 볼트 누적 바이트를 별도 제한하라. `readAll()`은 전체 문자열을 메모리에 보관하지 말고 스트리밍·페이지별 처리 또는 총 바이트 예산을 사용하라.

4. 위치: `src/tools.ts:299-311`, `test/unit/p2-11-23-input-normalization-limits.test.ts:174-181`

문제: 200KB 상한이 실제 응답 전체에는 적용되지 않는다.

근거: 본문을 `limit`까지 자른 뒤 다음 마커를 추가한다.

```ts
text.slice(0, i) + "\n…[truncated at 200 KB]\n"
```

따라서 응답은 200KB보다 마커 길이만큼 커진다. 테스트도 이를 알고 `TEXT_LIMIT + TRUNC_MARK.length`를 기대한다. `wiki_pack`은 `structuredContent.pages`를 별도로 제한하지만 `structuredContent.text` 역시 같은 초과를 가진다.

제안: 마커를 예산에 포함해 본문을 `limit - byteLength(marker)`까지 자르거나, 상한을 “본문 예산”으로 명확히 변경하라. 테스트는 `content[0].text`, `structuredContent.text`, `JSON.stringify(structuredContent)` 전체에 대해 상한을 검사해야 한다.

5. 위치: `src/cli.ts:78-88`, `src/once.ts:130-145`

문제: `--once`가 서버와 다른 root 결정 경로를 사용한다.

근거: `--once`는 `resolveRoot()`를 호출하지 않고 `runOnce()`에 raw `--root` 또는 `"."`를 전달한다.

```text
LLMWIKI_ROOT는 --once에서 사용되지 않음

```

`--once`는 MCP와 같은 retrieval 함수를 쓰지만 root 보안·검증·응답 상한은 동일하지 않다. 또한 `runOnce()`에는 `capText()`가 없어 대형 pack 결과를 무제한 stdout으로 출력한다. P2-33의 56개 패리티는 작은 fixture만 검사한다.

제안: root resolver를 `--once`와 서버가 공동 사용하게 하라. `--once`에도 vault 검증과 출력 상한을 적용하거나, P2-33 계약을 “retrieval 결과만 동일”로 명확히 축소하라.

6. 위치: `src/print-config.ts:49-51,64-65,84-86`

문제: Windows CLI 출력에서 env 전달만으로 CMD 메타문자 문제가 해결되지 않는다.

근거:

```ts
const envKV = `LLMWIKI_ROOT=${root}`;
map(shq).join(" ")
```

`shq()`는 `"`, `\`, `$`, 백틱만 escape한다. Windows CMD에서는 `%VAR%`와 지연 확장 `!VAR!`가 여전히 해석될 수 있다.

공격 경로:

```text
root = C:\vault%PATH%
root = C:\vault!SECRET!
root = C:\a&b
```

`&`는 따옴표 처리 상황에 따라 안전할 수 있지만 `%`와 `!`는 현재 escape되지 않는다. 테스트도 Windows 셸에서 실제 실행하지 않고 문자열에 `LLMWIKI_ROOT`가 존재하는지만 확인한다.

제안: Windows CLI 스니펫은 셸별 quoting을 분리하고, 가능한 경우 등록 명령 자체를 JSON/argv 구조로 출력하라. 최소한 `%`, `!`, quote, backslash, `&`, `|`, `^` 케이스를 실제 Windows 셸에서 검증하라.

## 1차 리뷰 반영 판정

- c-B2: `O_NOFOLLOW`와 POSIX 테스트는 실제 반영됨. 다만 위의 `root/wiki` 자체 symlink 누락으로 경계 보호는 불완전하다.
- c-B3: `capPages()`와 관련 테스트는 반영됨. 그러나 전체 200KB 계약은 마커 때문에 여전히 위반된다.
- c-M1/a-M2: 런타임 검증은 추가됐지만 독립 검증·input 검증이 없어 부분 수용이 정확하다.
- c-M2: 파일 수·파일 크기·동시 호출 상한은 반영됨. 누적 바이트·디렉터리·입력 전체 크기는 미해결이다.
- c-M3: 경로를 `--root`에서 env로 옮긴 것은 반영됐지만 Windows CLI env 값의 `%`/`!` 해석은 남아 있다.
- c-M6: debug 경로 제거는 반영됐고 selftest 경로 노출 유지 판정은 코드와 일치한다. 보안 관점에서는 이의가 있다.
- c-M8: “P2 범위에서 실제 Gemini/Codex/Cursor/Claude 검증을 하지 않는다”는 기각 사유에는 동의한다. 다만 P3 진입 조건으로 반드시 승격해야 한다.
- c-m2/a-m7: NFC/NFD 미정규화 기각은 Python 패리티 사유로 동의한다. 배포 한계 문서화는 필요하다.
- a-M1/a-m8: `--root` 위치 처리 및 read_page 이중 walk 제거는 코드에 반영됐다.
- P2-26 print-config: 스냅샷은 문법 문자열을 검증할 뿐 실제 Windows 셸·클라이언트 등록 성공을 검증하지 않는다.

## 총평(P3 진입 가능 여부)

현재는 P3 진입 불가다. `root/wiki` 자체 심볼릭 링크를 통한 외부 파일 유출, 검증되지 않은 테스트/CI 게이트, 누적 메모리·입력 자원 상한 부재가 우선 차단 사항이다. 그 다음 전체 응답 상한, `--once` root/parity 일관성, Windows 실제 셸 quoting, read-only guard를 보완하고 CI에서 재검증해야 한다.
