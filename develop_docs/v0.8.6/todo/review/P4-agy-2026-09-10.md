- **위치**: `tools/llmwiki-mcp/src/cache.ts:68`, `tools/llmwiki-mcp/src/cache.ts:173-177`
- **문제**: `snapshot` 함수에서 2초 신선도 창 검사 식 `now - st.mtimeMs < FRESH_WINDOW_MS` 는 `st.mtimeMs > now`(시계 오차, 타 머신 동기화, 압축 해제, git 체크아웃 등으로 미래 타임스탬프를 가진 파일)인 경우 `now - st.mtimeMs` 가 음수가 되어 **항상 `true` 로 평가**된다. 이로 인해 볼트 내 단 1개 파일이라도 미래 `mtime` 을 가지면 `snap.storable` 이 매 호출마다 `false` 가 된다. `readTexts` 는 `snap.storable` 이 `false` 일 때 `c.texts = new Map(); c.key = null; c.graph = null;` 을 실행하여 캐시를 통째로 비워버린다. 결과적으로 해당 볼트는 서버가 켜져 있는 동안 **캐시가 100% 무력화**되며 매 호출마다 디스크를 전량 다시 읽는다.
- **근거**:
  `src/cache.ts:68`:
  ```ts
  if (now - st.mtimeMs < FRESH_WINDOW_MS) storable = false; // 규칙 4
  ```
  `src/cache.ts:173-176`:
  ```ts
  } else if (c) {
    c.texts = new Map();
    c.key = null;
    c.graph = null;
  }
  ```
  실행 검증 (`node -e`):
  ```

  now - mtimeMs < FRESH_WINDOW_MS: true
  ```
- **제안**: 시간 차이를 양수 구간으로 한정하여 검사하도록 수정하라.
  ```ts

  if (ageMs >= 0 && ageMs < FRESH_WINDOW_MS) storable = false;
  ```

### [BLOCKER] 파일 수정 반복 시 `derivedBytes` 누적으로 128MiB 상한 초과 후 파생값 캐시 영구 비활성화

- **위치**: `tools/llmwiki-mcp/src/cache.ts:88`, `tools/llmwiki-mcp/src/cache.ts:91-98`, `tools/llmwiki-mcp/src/cache.ts:193-195`
- **문제**: `derivedBytes` 는 모듈 최상위 전역 변수(`let derivedBytes = 0;`)로 관리되며, 문자열 파생값(`haystack`, `scoreText`)이 계산될 때마다 누적된다. 그러나 동일 볼트 내에서 파일이 수정되어 그래프가 재조립(`assemble()`)될 때, `rootCache(base)` 는 `cur.base !== abs` 가 거짓이므로 `derivedBytes` 를 리셋하지 않는다. `derivedStore` 는 `WeakMap` 이라 이전 노드가 GC 되지만, 정수 카운터 `derivedBytes` 는 계속 증가만 한다. 따라서 10MB 규모 볼트에서 사용자가 노트를 13회 이상 수정하면 `derivedBytes >= DERIVED_BUDGET_BYTES(128MiB)` 상태가 영구 유지되어, 이후 모든 웜 호출에서 `derived()` 가 값을 저장하지 않고 매번 `pyLower`, `scoreText` 등을 재계산하게 된다(P4-13+ 파생 캐시 무력화).
- **근거**:
  `src/cache.ts:193-195`:
  ```ts
  if (derivedBytes >= DERIVED_BUDGET_BYTES) return value; // 상한 초과 — 저장하지 않는다
  if (typeof value === "string") derivedBytes += Buffer.byteLength(value, "utf8");
  ```
  실행 검증 (동일 볼트 10MB 노드 15회 갱신 시뮬레이션):
  ```
  Edit 12: derivedBytes = 120.0 MB
  Edit 13: derivedBytes = 130.0 MB
  Edit 14: derivedBytes = 130.0 MB
  After limit exceeded: computed count = 2 (expected 1 if cached, got 2)
  ```
- **제안**: 그래프가 새로 조립되거나 교체될 때(`setGraph` 또는 `cur.key = null` 시점) `derivedBytes` 를 0으로 리셋하거나, `derivedBytes` 를 `RootCache` 객체 내부 필드로 이관하여 그래프 수명과 동기화하라.

### [MINOR] 단일 슬롯 전역 변수 `cur: RootCache` 로 인한 동시/교차 볼트 요청 시 레이스 컨디션

- **위치**: `tools/llmwiki-mcp/src/cache.ts:87-98`
- **Problem**: `cur` 가 단일 인스턴스 전역 변수(`let cur: RootCache | null = null;`)로 선언되어 있어, 서로 다른 볼트 경로를 번갈아 조회할 때 캐시가 매번 전량 파기된다. 비동기 I/O(`readTexts`) 도중 다른 `base` 가 인입되면 `c.texts` 대입과 `cur` 간의 참조 불일치가 발생할 수 있다.
- **근거**:
  `src/cache.ts:91-97`:
  ```ts
  function rootCache(base: string): RootCache {
    const abs = path.resolve(base);
    if (!cur || cur.base !== abs) {
      cur = { base: abs, key: null, graph: null, texts: new Map() };
      derivedBytes = 0;
    }
    return cur;
  }
  ```
- **제안**: stdio 환경에서는 `--root` 가 고정이므로 치명적이지 않으나, `Map<string, RootCache>` 구조로 전환하여 경로별 캐시를 분리 관리하는 것이 안전하다.

### 총평 (병합 가능 여부)

**병합 불가 (Merge Blocked).** 미래 `mtime` 파일을 가진 볼트에서 캐시가 전면 무력화되고 매 요청마다 캐시 엔트리를 강제 초기화하는 결함(`cache.ts:68`)과, 동일 볼트에서 파일 수정이 누적될 때 `derivedBytes` 가 리셋되지 않아 128MiB 상한 초과 후 파생값 캐시가 영구적으로 정지하는 결함(`cache.ts:193`) 등 **[BLOCKER] 2건**이 존재한다. 또한 CI 상에서 캐시 비활성화(`LLMWIKI_CACHE=0`) 패리티 검증이 누락되어 있어 DoD 조건을 충족하지 못하고 있다. 지적된 [BLOCKER] 2건과 [MAJOR] CI 구성을 보완한 뒤 재리뷰를 거쳐 병합해야 한다.
