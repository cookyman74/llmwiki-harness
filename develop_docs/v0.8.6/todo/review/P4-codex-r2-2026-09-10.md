[BLOCKER] `FRESH_WINDOW_MS`가 기존 캐시 적중을 차단하지 않음

- 위치: `tools/llmwiki-mcp/src/cache.ts:121-124, 185-189, 203-211`; `src/graph.ts:35-38`
- 문제: 최근 수정 파일이면 `storable=false`가 되지만 `getGraph()`는 `snap.storable`을 확인하지 않습니다. 기존 키와 같으면 그래프를 즉시 반환합니다. 그래프 적중이 아니어도 `readTexts()`는 `storable`과 무관하게 같은 `FileId`의 텍스트를 재사용합니다.
- 근거: `getGraph()` 조건은 `c.key === snap.key`뿐입니다. 현재 테스트 `p4-cache.test.ts:87-100`은 첫 호출부터 캐시가 저장되지 않는 상황만 시험하므로, “기존 캐시 저장 → 같은 메타데이터의 최근 수정” 경로를 검증하지 않습니다.
- 제안: `!snap.storable`이면 그래프 적중을 금지하고, `readTexts()`도 모든 파일을 재독하도록 하십시오. 해당 순서의 회귀 테스트를 추가해야 합니다.

[BLOCKER] 상위 디렉터리 교체 경쟁에서 realpath 경계가 우회됨

- 위치: `tools/llmwiki-mcp/src/vault.ts:194-217, 224-240`; `src/cache.ts:89-103`
- 문제: `walkMd()`의 realpath 검사가 끝난 뒤 `wiki/L3` 같은 상위 디렉터리를 외부 디렉터리의 심볼릭 링크로 교체하면, `lstat(path)`와 `read(path)`는 상위 링크를 따라갑니다. `O_NOFOLLOW`는 최종 구성요소만 보호하며 상위 디렉터리는 보호하지 않습니다. Windows에서는 `O_NOFOLLOW`가 0입니다.
- 근거: DESIGN §5가 이 경쟁을 “수용된 잔여 위험”으로 기록하지만, 실제로는 외부 파일 내용이 그래프에 들어가 캐시될 수 있습니다. P4 테스트에는 결정론적 경쟁 테스트가 없습니다.
- 제안: 디렉터리 핸들 기반 `openat`/`O_NOFOLLOW` 순회 등으로 각 경로 구성요소를 고정하십시오. 불가능하면 해당 플랫폼에서 캐시·외부 경로 접근을 보수적으로 비활성화해야 합니다.

[BLOCKER] Windows·일부 네트워크 파일시스템에서 `ctimeNs` 방어가 성립하지 않음

- 위치: `tools/llmwiki-mcp/src/cache.ts:16-18, 38-40, 82-85`
- 문제: 코드 주석 자체가 Windows의 `ctimeNs`를 생성 시각으로 인정합니다. Windows에서 파일 내용을 같은 크기로 덮어쓰고 mtime을 복원하면 dev/ino/mode/size/mtime/ctime이 모두 같을 수 있어 낡은 텍스트가 적중합니다. 컨테이너·네트워크 FS도 ctime 갱신 보장이 약합니다.
- 근거: CI가 `windows-latest`를 포함하지만 `p4-cache.test.ts:204-220`의 ctime 회귀는 POSIX식 ctime 갱신을 전제로 합니다.
- 제안: 플랫폼별 ctime을 신뢰하지 말고 내용 해시 또는 열린 파일 디스크립터에서 읽은 내용 검증을 사용하십시오. 최소한 Windows에서는 동일 메타데이터 적중을 허용하지 않아야 합니다.

[MAJOR] 텍스트·파생 메모리 상한이 실제 상한이 아님

- 위치: `tools/llmwiki-mcp/src/cache.ts:144-168, 230-246`; `src/graph.ts:38-42`
- 문제: `TEXT_BUDGET_BYTES` 초과 시 텍스트 Map과 그래프를 비우지만, 곧바로 `assemble()`한 그래프를 `setGraph()`가 다시 저장합니다. 그래프가 모든 본문 문자열을 보유하므로 256MiB 상한을 우회합니다. 또한 최대 4개 root의 그래프가 살아 있는데 `derivedBytes`는 전역 단일 카운터이며 새 그래프마다 리셋됩니다.
- 근거: `setGraph()`에는 텍스트 예산 상태가 전달되지 않고, `roots`가 최대 4개 그래프를 보유합니다. WeakMap도 그래프가 root cache에서 살아 있는 동안 파생값을 회수하지 않습니다.
- 제안: 텍스트 예산 초과 시 그래프도 저장하지 말고, root별 예산을 계산하십시오. 파생값은 실제 보유 그래프 전체를 기준으로 집계하거나 root eviction 시 명시적으로 폐기해야 합니다.

[MAJOR] CI가 캐시 적중·무효화 패리티를 실제로 검증하지 않음

- 위치: `.github/workflows/ci.yml:57-68`; `tests/parity.py`; `tests/parity_fuzz.py`
- 문제: `parity.py`와 fuzz는 매 케이스마다 새 `node dist/cli.js` 프로세스를 실행하므로 캐시 적중 경로를 시험하지 않습니다. CI의 on/off도 “cold 실행” 비교입니다. 파일 수정, root 전환, 권한 변경, 최근 mtime 상황의 on/off 연속 호출은 CI에서 재현되지 않습니다.
- 근거: `parity.py`의 `node_command()`가 매번 새 subprocess를 만들고, fuzz도 동일합니다. 연속 호출 검증은 로컬 Vitest에만 있습니다.
- 제안: CI에 동일 Node 프로세스에서 `build → hit → mutate → rebuild`를 수행하는 통합 테스트를 추가하고, 캐시 on/off 양쪽에서 결과를 비교하십시오.
