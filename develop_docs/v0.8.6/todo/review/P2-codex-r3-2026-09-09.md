1. 위치: `.github/workflows/ci.yml:73-96`, `P2-mcp-server.md:78,105,109`

문제: 읽기 전용 CI 가드가 `open`의 별칭 import를 통한 쓰기를 차단하지 못한다.

근거:

```ts
import { open as create } from "node:fs/promises";
await create("x", "w");
```

`orig === "open"`이라 import 허용목록을 통과하지만, `create(...)`는 `fs.open(...)` 패턴에 매치되지 않는다. 쓰기 플래그 검사도 우회된다. 따라서 P2-48+의 “쓰기 경로 0 보장”은 성립하지 않는다.

제안: import별 로컬 바인딩을 추적하는 AST 검사로 바꾸고, `open` 별칭 호출에도 쓰기 플래그 검사를 적용하라. 허용목록 fixture에 별칭 공격 케이스를 추가하라.

## [MAJOR]

3. 위치: `tools/llmwiki-mcp/src/pack.ts:61-84`, `src/server.ts:93-99`

문제: `wiki_pack`은 입력 30개 × 파일 16MiB까지 모두 읽고 `claims`/`relations` 배열을 만든 뒤에야 `capPages()`를 적용한다.

공격 입력:

```json
{"slugs":["p1","p2", "...", "p30"]}
```

각 페이지가 16MiB이면 약 480MiB의 원문·파싱 결과가 누적될 수 있다. `MAX_TOTAL_BYTES`는 `readAll()` 경로에만 적용되고 `pack()`에는 적용되지 않는다.

제안: pack 전용 누적 바이트 예산을 파일 read 및 claim 추출 전에 적용하라. 페이지별 결과를 즉시 제한하고, 상한 초과 시 다음 페이지를 읽지 말고 `isError`로 종료하라.

4. 위치: `tools/llmwiki-mcp/src/server.ts:79-99`, `src/tools.ts:329-340`

문제: 200KB 제한이 `content[0].text`와 `structuredContent.pages`에 각각 적용된다. `wiki_pack`의 실제 구조화 응답 전체는 약 400KB까지 커질 수 있다.

근거:

```ts
structuredContent: {
  text,
  pages: capped.pages,
  truncated: ...
}
```

테스트도 `JSON.stringify(pages)`만 검사하고 `JSON.stringify(structuredContent)` 전체는 검사하지 않는다(`p2-11-23-input-normalization-limits.test.ts:188-208`).

제안: MCP 응답 전체 예산을 하나로 관리하고 `text`, `pages`, JSON envelope를 합산해 절단하라. 전체 직렬화 크기 테스트를 추가하라.

5. 위치: `tools/llmwiki-mcp/src/server.ts:90`, `src/format.ts:19-20,24-27`, `test/unit/p2-09-output-schema.test.ts:79-99`

문제: `structuredContent`를 지원하지 않는 클라이언트에서는 `wiki_expand`의 다음 라우팅 정보가 사라진다.

6. 위치: `tools/llmwiki-mcp/test/unit/p2-21-symlink-leak.test.ts:46-52,63-104`

문제: 심볼릭 링크 생성 실패 시 `return`만 하므로 테스트가 성공한 것으로 집계된다.

근거:

```ts
if (!canSymlink) {
  console.error(`SKIP: ${skipReason}`);
  return true;
}
```

각 `it()`가 `if (skip()) return`으로 끝나며 `it.skip()`이나 실패 처리가 아니다. Windows에서 권한이 없으면 4개 보안 테스트가 모두 실행되지 않아도 CI가 녹색이 될 수 있다.

제안: `it.skipIf(!canSymlink)`를 사용하고 CI 결과에서 skipped를 별도 실패 조건 또는 명시적 조건부 검증으로 관리하라.
